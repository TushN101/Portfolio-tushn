Technical Assessment of University Mobile Application

Static analysis of an educational mobile application identified hardcoded signing secrets, unauthenticated database endpoints, and cleartext communications.

TN
TushN101 Android Technical Assessment · 5 min read
All research

Disclaimer: All sensitive credentials, cryptographic secrets, internal IP addresses, and identifiers in this article have been redacted to ensure responsible disclosure and safeguard system integrity. The reported vulnerabilities were responsibly disclosed to institutional administration and have been confirmed fixed and mitigated.

Introduction

University mobile applications frequently interface with sensitive student records, attendance systems, and internal campus services. To evaluate the security posture of mobile software distributed in educational environments, I conducted a static security analysis of the official Android mobile application provided to students.

Using a custom static analysis and decompilation tool built in C++, I automated the extraction and inspection of the application package (APK) resources, manifests, and compiled configurations to identify potential security weaknesses.

Findings

1. Insecure Network Configuration

android:usesCleartextTraffic="true"

The application manifest permitted unencrypted cleartext HTTP traffic. Transmitting data over unencrypted HTTP allows network eavesdroppers on the same wireless network to inspect and tamper with communication in transit.

2. Hardcoded Google API Key

<string name="google_api_key">AIzaSyCY1WECCTOt1kmuZDQVD_XXXXXXXXXXXXX</string>

A Google API key was embedded directly in the application configuration. While its active scope was restricted at the time of evaluation, embedding API keys without strict service or package restrictions introduces risk if backend permissions are broadened in the future.

3. Exposed Firebase Realtime Database

<string name="firebase_database_url">https://[REDACTED_APP].firebaseio.com</string>

The Firebase database was configured without proper authentication rules, leaving the default REST endpoint accessible to unauthenticated clients: 

curl https://[REDACTED_APP].firebaseio.com/.json

4. Hardcoded JWT Secret & Salt Keys

"AppKey": {
    "saltKey":   "25-+c$jdPK^c^yXPEPV4[REDACTED_SALT_KEY]",
    "secretKey": "XSz4V8UBdu@T#%Y&HNpp[REDACTED_JWT_SECRET]"
}

The configuration file contained static cryptographic signing keys used for issuing and verifying JSON Web Tokens (JWTs). Hardcoding symmetric signing secrets in client applications undermines the entire authentication model, as any party with access to the application package can read the secret.

5. Internal Server IPs & Staging Endpoints

"LiveServer": {
    "myApiUrlHostel":   "http://10.130.XX.XX:8087/Hostel/api/",
    "myApiUrlLms":      "http://[REDACTED_IP]:8081/",
    "myApiUrlUsermgmt": "http://[REDACTED_IP]:8081/usermgmt/",
    "myInfraApiUrl":    "https://[REDACTED_DOMAIN]:3000/"
}

The bundle contained internal IP addresses and service routes for student hostels, learning management systems (LMS), and user administration, exposing details of the institution's internal network topography.

Vulnerability & Risk Analysis

Token Signing and Authorization Risks

When an application utilizes symmetric encryption for JWTs, the same key is used to both create and verify tokens. With the signing secret exposed:

  • A client could craft arbitrary token claims, including elevated privileges such as administrator or faculty roles.
  • Backend services verifying signatures with the shared secret would accept the forged token as legitimate.
  • This could allow unauthorized access to administrative functions, student records, and course management systems.

Ethical Testing Boundary: In accordance with responsible disclosure principles, no unauthorized tokens were generated or used against live systems, nor was any unauthorized access attempted. The vulnerability was documented solely through static code analysis.

Responsible Disclosure & Remediation

Upon documenting these findings, a comprehensive security advisory was compiled and submitted directly to university technical administration and institutional leadership.

The administration acknowledged the report and promptly initiated remediation. The vulnerabilities were reported, addressed, and mitigated:

  • The compromised JWT secrets and salts were revoked and replaced with secure, server-side asymmetric key signing (RS256).
  • Firebase database security rules were updated to enforce strict authentication requirements.
  • Internal IP addresses and staging endpoints were stripped from client release builds.
  • Cleartext traffic was disabled, enforcing HTTPS across all mobile communications.
