Encrypted File Sharing Website Vulnerability

Found a bug in the implementation of file encryption leading to full exposure of files shared online.

Background

If you haven't read the previous writeup, the short version is: the PocketBase API behind this file sharing platform was completely open. No authentication, no access rules one curl command and you had every file ever uploaded.

After that report, the developer got to work. The main fix was encryption files would now be encrypted using the access code assigned to them before being stored on the server. The server would only ever hold encrypted blobs. On paper, a solid response.

Back to Square One Almost

I ran my old script against the updated platform. It could still list files and see their names a minor PII leak, but not much else. The real problem was that every download was coming back as an encrypted blob. Useless without the code. The contents were now genuinely hidden.

I started digging through the frontend source code to figure out what was happening maybe files were being zipped, maybe it was streaming data differently. The developer had privated the repo after the previous exploit, so I only had what was visible in the browser. I fed some of that to Gemini to help make sense of it. It pointed towards encryption, which I confirmed by testing an actual download.

I poked around for other weaknesses for a while and came up empty. Then I took a closer look at the raw API response.

Noticing the Hash Field

There was a field in the listing that wasn't there before: unique. My first assumption was that it was a checksum of the file integrity verification, something like that. It wasn't. I uploaded a test file and compared the hash against the file contents. No match.

So I tried something else. I uploaded another file, noted the code I received, calculated the hash of that code, and checked which hash was stored.It matched the hash of the code. The developer was storing a hash of each file's access code in the public API response most likely so the frontend could verify a user's input quickly without the server having to attempt a full decryption every time someone guessed wrong.

The moment I confirmed that, the rest was obvious.

The Exploit

Hashes aren't reversible , but the input space here is tiny. Access codes are 4 digits. That's 10,000 possible values, from 0000 to 9999. Building a lookup table of every possible hash takes milliseconds.

I got AI to write the script. I honestly expected the table generation to take a noticeable amount of time. It finished before I could even check if it was running. From there it was just combining this with my old listing script: pull all file records from the API, grab the stored hash for each one, look it up in the table, recover the code, use the code to decrypt the file.

Every "encrypted" file on the platform was fully recoverable. The encryption itself was real , the key management was the problem. If the hash of your key is sitting in a public API response and the key is a 4-digit number, we don't have encryption.

What Changed After

The developer has since pushed further fixes:

  • Row-Level Security (RLS) files can no longer be bulk-listed; a specific identifier is now required to look up any individual record
  • File History users can now manually delete their own uploaded files
  • Infrastructure hardening moving off the free PocketHost tier to something with proper CORS and Nginx shielding

The developer has done really great work. I’ve reported few bugs on this website, and I think it’s time for me to step back now. Wishing the developer all the best.
