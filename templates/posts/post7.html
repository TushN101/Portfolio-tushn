Master API Key Exposure: Infrastructure-Wide Compromise

Discovery of an exposed super-admin API key in client-side requests, enabling administrative access to user PII, credentials, and storefront configurations.

Disclaimer: The API key shown in the screenshots and blog post has since been rotated and is included solely for demonstration and educational purposes.

We begin with the main landing page of qobo.dev. At first glance, it appears to be a standard WhatsApp-to-Website builder, but examining the client-side communication reveals significant architectural weaknesses.

1. Enumeration and Subdomain Discovery

I started with initial reconnaissance to map out the infrastructure. The results revealed several internal and client-facing subdomains that expanded the assessment surface.

Testing the Infrastructure

testing.qobo.dev

This route was publicly accessible. It serves as a dynamic project link generator, allowing subdomains to be provisioned on demand.

By entering an arbitrary project string (for example, "test-demo"), the system allows the creation of a persistent subdomain (test-demo.testing.qobo.dev) without authentication. Unauthenticated subdomain provisioning represents a configuration weakness that warrants stricter access controls.

swaadhome.qobo.dev

This subdomain hosts a live production site built for a client business—Anjali Mehta's homemade snacks.

2. Intercepting the Master API Key

While reviewing network requests on the client site, I intercepted a background call to /api/v1/product_rates. While fetching product catalog details is standard application behavior, inspecting the request headers revealed a critical vulnerability:

The X-API-KEY header was being sent directly in client-side browser requests:

X-API-KEY: qobo_fb9194b6-bb10-40cc-94a3-9b30c1f96544_ae27882edbdf2204f94976ac968bc81a

3. Excessive Privileges and Administrative Endpoint Access

Reviewing the API route definitions within the client bundle revealed that this key was not scoped strictly for read-only pricing data. Instead, it operated as a master administrative key with permissions spanning user management, site configurations, and order processing.

User Data Exposure

Supplying this key to the /api/v1/users endpoint returned the complete user database, including names, contact numbers, email addresses, stored passwords, and session tokens.

Similarly, querying the order endpoints exposed sensitive customer delivery addresses and financial transaction details.

Furthermore, administrative access extended to payment configurations. An unauthorized party possessing these credentials could modify merchant payment details (such as UPI IDs or QR codes), posing significant financial integrity risks to businesses hosted on the platform.

4. Proof of Concept: Rate Modification

To verify whether the exposed key permitted state-changing operations, a test request was made to modify the rate of a sample item ("Fried Modak", originally ₹25.00).

A PUT request using the intercepted API key updated the item rate:

Reloading the page in an incognito session confirmed that the backend had updated the price globally in the database.

Note: To preserve data integrity during verification, the price was immediately restored to its original value.

Conclusion and Impact Assessment

Exposing administrative credentials in client-side code introduces significant operational and security risks, including:

  • Unauthorized Configuration Changes: Modifying store names, links, and catalog details.
  • Pricing and Catalog Manipulation: Modifying product pricing or altering checkout amounts.
  • Sensitive Data Exposure: Unrestricted access to customer PII and credentials.
  • Payment Redirection: Modifying payment destination details to divert customer payments.

Investigation showed that identical credential handling affected other tenant domains, highlighting the vulnerability inherent in using shared administrative credentials across multi-tenant web applications.

Responsible Disclosure and Remediation

The vulnerability was responsibly reported to the platform development team. The maintainers acknowledged the report and subsequently resolved the issue. To mitigate future risk, the backend architecture was migrated to Supabase, eliminating reliance on client-side API keys and enforcing granular row-level security policies.
