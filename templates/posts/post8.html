Building Full-Stack Observability with Prometheus & Grafana

From zero to live monitoring: instrumenting Python web services, gathering host telemetry with Node Exporter, crafting real-time dashboards, debugging label mismatch traps, and setting up automated threshold alerts.

TushN101 Systems & Architecture · 8 min read

1. The Core Architecture: Why Prometheus & Grafana?

When running web applications and server infrastructure, you quickly discover that logs alone are not enough. While application log streams tell you what happened during a failure, metrics tell you how healthy the system is over time—tracking traffic spikes, memory leaks, latency degradation, and error rate surges before complete crashes occur.

To build a complete observability pipeline, we need to understand the distinct responsibilities of each tool in the telemetry stack:

  • Application Exporters (e.g. prometheus_flask_exporter): Web frameworks like Flask do not natively track time-series history. The exporter middleware measures incoming HTTP request rates, latencies, and response codes, exposing them as formatted text on an HTTP endpoint (typically /metrics).
  • Node Exporter: Runs as a lightweight system daemon to extract hardware- and kernel-level metrics from the operating system—including CPU ticks, memory utilization, disk I/O, and network bandwidth.
  • Prometheus: The storage and ingestion engine. Prometheus uses a pull-based architecture: at configured intervals (e.g., every 5 seconds), it scrapes the HTTP /metrics endpoints of registered targets, stores them in an optimized local Time-Series Database (TSDB), supports PromQL queries for arithmetic and rate calculation, and evaluates alerting rules.
  • Grafana: The visualization layer. Grafana does not store metrics itself. Instead, it queries Prometheus as a data source and renders interactive dashboards, time-series charts, single-stat gauges, and heatmaps.

Architecture Flow: [Flask App / Node Exporter] → (Pulls over HTTP /metrics) → [Prometheus TSDB] → (PromQL queries) → [Grafana Dashboard & Alerts]

2. Installation & Environment Setup

For this walkthrough, we set up Prometheus, Grafana OSS, and Node Exporter directly on a Linux environment using official standalone binaries.

1. Installing Prometheus

# Download and extract Prometheus
wget https://github.com/prometheus/prometheus/releases/download/v3.16.0/prometheus-3.16.0.linux-amd64.tar.gz
tar -xvf prometheus-3.16.0.linux-amd64.tar.gz
cd prometheus-3.16.0.linux-amd64

2. Installing Grafana OSS

# Download and extract Grafana OSS
wget https://dl.grafana.com/grafana/release/13.3.1/grafana_13.3.1_42849527790_linux_amd64.tar.gz
tar -zxvf grafana_13.3.1_42849527790_linux_amd64.tar.gz

3. Installing Node Exporter

cd node_exporter-1.13.1.linux-amd64

3. Phase 1: Host Telemetry with Node Exporter

We begin by monitoring the host operating system. Starting the node_exporter binary binds by default to port :9100: 

./node_exporter

Next, we instruct Prometheus to scrape this endpoint by configuring prometheus.yml: 

global:
  scrape_interval: 15s

scrape_configs:
  - job_name: 'node'
    static_configs:
      - targets: ['localhost:9100']

Starting Prometheus (./prometheus --config.file=prometheus.yml) and navigating to http://localhost:9090/targets confirms the connection. The target status displays as healthy and UP:

Querying Host Metrics with PromQL

Prometheus provides a powerful query language, PromQL. Beyond viewing raw numbers, we can compute derived statistics. For instance, to calculate the percentage of memory currently in use across our Linux system: 

100 * (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)

Connecting Grafana & Building Host Dashboards

We now launch Grafana by running ./bin/grafana server and accessing the web console at http://localhost:3000 (default credentials: admin / admin):

Under Connections > Data Sources, we add Prometheus with the URL http://localhost:9090. In the Explore view, we can immediately query system metrics such as node_cpu_seconds_total:

4. Phase 2: Application Telemetry with Flask

Host metrics tell us if the machine is overloaded, but they cannot tell us if our web service is serving customer requests reliably. To track the Golden Signals (Traffic, Latency, and Errors), we instrument a Python Flask application.

We install the exporter library:

pip install prometheus_flask_exporter

Next, we write an instrumented application (app.py):

from flask import Flask
from prometheus_flask_exporter import PrometheusMetrics

app = Flask(__name__)

# Attach metrics middleware with an application label
metrics = PrometheusMetrics(app, static_labels={'app_name': 'python_app'})

@app.route('/')
def index():
    return "Hello World", 200

if __name__ == '__main__':
    app.run(
        debug=True,
        use_reloader=False,
        port=8000,
        host='0.0.0.0'
    )

We then add a scrape job for our Python web application in prometheus.yml: 

scrape_configs:
  - job_name: 'python_app'
    scrape_interval: 5s
    scrape_timeout: 5s
    static_configs:
      - targets: ['localhost:8000']

With Flask running on port 8000 and Prometheus scraping it every 5 seconds, querying flask_http_request_total in the Prometheus UI visualizes incoming HTTP traffic in real time:

5. Troubleshooting: The “No Data” Label Mismatch Trap

A frequent stumbling block when importing community Grafana dashboards is loading a dashboard only to find every panel displays No data:

Root Cause Analysis

Understanding why this happens requires distinguishing between two distinct configuration concepts:

  • static_configs (Who to scrape): Defines network targets (e.g., localhost:8000). Prometheus successfully scrapes these targets and marks them UP.
  • static_labels and Dashboard Variables (What to filter): Pre-built Grafana dashboards use dashboard-level template variables (such as $app_name or $job) in panel queries: 
    flask_http_request_total{app_name="$application_name"}

If the dashboard variable expects flask-monitoring, but your application exporter defines 'app_name': 'python_app', the PromQL query evaluates to an empty result set.

The Fix: Either update the static_labels key-value pairs in your Python exporter to match what the dashboard template expects, or modify the dashboard variable dropdown in Grafana (under Dashboard Settings > Variables) to query label_values(app_name) dynamically. Once aligned, metrics flow seamlessly into every panel.

6. Phase 3: Threshold Alerting with Prometheus Rules

Dashboards are indispensable during debugging, but no engineering team stares at monitoring screens 24/7. Production observability requires alert-driven detection that notifies engineers the moment an anomaly or outage occurs.

We create an alerting rule file, alert_rules.yml, to trigger when our web application stops responding: 

groups:
  - name: flask_app_alerts
    rules:
      - alert: FlaskAppDown
        expr: up{job="python_app"} == 0
        for: 30s
        labels:
          severity: critical
        annotations:
          summary: "Flask application is down"
          description: "Prometheus cannot scrape {% raw %}{{ $labels.instance }}{% endraw %} for more than 30 seconds."

We link this rule set inside prometheus.yml:

global:
  scrape_interval: 5s

rule_files:
  - "alert_rules.yml"

scrape_configs:
  - job_name: 'python_app'
    scrape_interval: 5s
    scrape_timeout: 5s
    static_configs:
      - targets: ['localhost:8000']

The Alert Lifecycle in Action

To test the rule, we terminate the Flask application process (Ctrl + C). Prometheus handles the outage across three sequential states:

  1. Inactive (Green): The application is up, and up{job="python_app"} == 1.
  2. Pending (Yellow): The condition up == 0 evaluates to true. However, because we configured for: 30s, Prometheus holds the alert in a pending state. This threshold damping prevents alert fatigue from momentary network blips or brief process restarts.
  3. Firing (Red): Once the application remains unreachable for a full 30 seconds, the alert transitions into FIRING state:

In enterprise setups, Prometheus forwards firing alerts to Alertmanager, which deduplicates notifications, manages silences, and routes dispatches to Slack, Discord, PagerDuty, or custom webhook endpoints.

7. Summary & Observability Checklist

Through this hands-on exploration, we established an end-to-end monitoring pipeline:

  • Infrastructure Visibility: Node Exporter captures low-level kernel and hardware statistics without touching application code.
  • Service-Level Metrics: Middleware exporters expose application-specific Golden Signals (throughput, latency, error status codes).
  • Label Consistency: Dashboard queries depend directly on metric label fidelity; aligning static labels prevents "no data" anomalies.
  • Automated Escalation: Threshold rules with temporal damping (for: 30s) eliminate false alarms while guaranteeing immediate escalation when critical components fail.
